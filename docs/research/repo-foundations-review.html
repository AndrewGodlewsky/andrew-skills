What should a repo-creation skill set up?

A researched guide to intent, language, architecture, agent instructions, and the supporting structures that help successive agents make coherent changes.

Create the smallest useful set of authoritative artifacts.

Start with purpose, vocabulary, a first verifiable outcome, and working setup/check commands. Add architecture, decisions, contracts, and operations guidance when the project needs them.

Baseline means a responsibility to address, not a mandatory new file. Reuse a README section, existing CONTEXT.md, contributor guide, or accessible issue tracker when it already serves the purpose.

Filename is not a loading guarantee. Make custom documents discoverable through the chosen agent's supported entry point, with task-based reading triggers. Verify its actual loading and scope behavior.

In this guide, domain can mean a document's subject areas (purpose, testing, compatibility) or the project's business/technical areas (billing, authentication, package distribution). The creation skill should identify both without inventing unnecessary layers.

Review scope: this document proposes a future skill. It does not install or implement it, change existing repository policy, or mandate all the files shown below.
02 / Research findings

Separate observed practice from proposed design.

Empirical findings describe repositories or measured agent behavior. First-party practice documents what an author or engineering team does. Proposed design is the synthesis in this guide. No study here proves this entire file bundle is optimal.

  • Agent READMEs supplies a 16-category taxonomy from 332 manually reviewed files sampled from a 2,303-file corpus. Use it as a coverage prompt, not a requirement to include every category.
  • Evaluating AGENTS.md, v3 reports no general task-success improvement and over 20% greater average inference cost in its settings. This supports evaluating concise, relevant guidance rather than assuming volume helps.
  • Configuration Smells, v5 studies 100 popular repositories with heuristic detectors, identifying recurring problems such as lint-rule duplication and excess context. It does not establish universal word limits.
  • The September 2026 ADR study analyzes 4,316 records across 547 repos and highlights gaps around alternatives and decision drivers. Automated label agreement of 46–66% limits strong conclusions.
  • SpecMine offers an observational corpus of specification artifacts and links to changes. It supports later comparison, not claims that a particular template works best.

The OpenAI and Anthropic harness accounts support structured knowledge and executable feedback in their engineering settings. They are case studies, not controlled comparisons of every proposed repository layout.

Source-specific evidence for the artifact contents
  1. Empirical: Prana and colleagues, Categorizing the Content of GitHub README Files, first submitted in 2018, manually annotated 4,226 sections from 393 randomly sampled repositories. Descriptions of functionality and usage were common; explanations of purpose and project status were often missing. This supports explicitly checking those omissions, not prescribing a universal template.
  2. Platform practice: GitHub's README guidance identifies purpose, usefulness, getting started, help, and maintainers as typical contents. GitHub surfaces a README from .github, repository root, or docs, in that order.
  3. Vendor workflow: Anthropic's Capture as intent.md describes a human-reviewed proto-spec for an idea, ticket, or incident. An intent/ directory is suggested for one product. This is a change-level workflow convention, not a universal specification for a root INTENT.md.
  4. Practitioner concept: Fowler on Ubiquitous Language explains developing shared language with domain experts and using it consistently in discussion and code.
  5. Practitioner concept: Fowler on Bounded Context explains that a coherent model has a defined boundary; meanings can differ across contexts and their relationships need explicit treatment.
  6. Documentation framework: arc42's glossary guidance includes important domain and technical terms, with optional translations, so stakeholders understand words consistently.
  7. Executable authoring practice: GitHub Spec Kit's spec template and clarification workflow separate user scenarios, requirements, entities, measurable outcomes, and assumptions; clarification checks missing scope, data, UX, quality, integration, failure, terminology, and completion decisions. These are maintained templates, not empirical proof of effectiveness.
  8. Executable specification practice: Cucumber's Gherkin reference connects an initial situation, an event, and an observable result. Scenarios become executable only when supported by corresponding step definitions and a runner.

The file outlines and setup workflow below are proposed synthesis, tailored to a skill creating a new repository. The cited architecture methods are established practitioner guidance, and OpenAPI is a technical specification. None proves that this exact file bundle improves coding-agent outcomes.

There is relevant empirical content research: a September 2026 preprint analyzes 4,316 ADRs from 547 repositories. It identifies missing or misplaced alternatives and decision drivers. Its automated taxonomy agreement with human labels was 46–66%, and its filters exclude projects with fewer than five ADRs. Treat it as evidence of documentation gaps, not a universal quality score or an agent-performance experiment. Miccio, Tommasel, and Diaz-Pace

The useful objective is answerability: can the next agent find where a behavior belongs, distinguish current facts from proposals, understand a consequential choice, and check the constraints it must preserve?

The strongest directly relevant accounts are first-party engineering case studies. OpenAI describes a short agent entry point, a navigable documentation system, executable boundary checks, and accessible diagnostics. Anthropic describes session continuity supported by initialization scripts, feature criteria, progress records, and verification. Neither establishes that every repository benefits from an identical file tree. OpenAI, Anthropic.

The proposed creation skill should produce usable capabilities, with documents explaining them. A command that actually checks a property is stronger evidence than a paragraph saying that the property matters. A small repository can put several responsibilities in one file. An operational service may need more distinct documents than a library or collection of content.

Earlier research: what agent instruction files contain across GitHub

Research checked October 7, 2026. Several empirical studies compare the contents of AGENTS.md, CLAUDE.md, and related files across GitHub repositories. These studies describe existing practice; prevalence alone does not establish that an instruction improves agent performance.

Content and writing styles in AGENTS.md

Context Engineering for AI Agents in Open-Source Software, October 24, 2025, examined adoption in 10,000 repositories, found 466 with supported configuration files, and investigated a collected set of 155 AGENTS.md files. Its content analysis applies additional exclusions and focuses on recurring first- and second-level headings.

Its 14 categories distinguish coding conventions, contribution procedures, architecture, build commands, project descriptions, test execution, test strategy, metadata, dependencies, setup, references, troubleshooting, examples, and security. Its table counts headings, not percentages of repositories. It also identifies five ways of expressing instructions: descriptive, prescriptive, prohibitive, explanatory, and conditional. This is useful when comparing how files communicate rules, beyond which subjects they mention. Sections 4.2 and Table 1; supplementary material.

Baseline responsibilityINTENT.mdDurable purpose, desired outcomes, priorities, and non-goals.

Purpose and creation trigger. Proposed design: preserve the durable reason for this repository, especially when several plausible implementations would satisfy an immediate feature request but serve different long-term goals. Create a dedicated intent document when scope, priorities, or exclusions would otherwise disappear into chat. A short README purpose section may be sufficient for a small utility. Preserve an existing product brief, charter, or intent record as authoritative rather than generating a competing one.

Anthropic's source describes a different, useful granularity: each proposed change has its own intent record, reviewed by its product owner before progressing. A setup skill should ask whether the user wants durable project intent, change proposals, or both, and make the distinction visible. Capture as intent.md.

Proposed content domains:

  • Problem and evidence: today's difficulty, affected people, concrete examples, source links, and assumptions requiring validation.
  • Desired outcome: the capability or improvement sought, the main beneficiaries, and how success would be recognized.
  • Scope: included work, explicit exclusions, first-release boundary, and relationships to adjacent products.
  • Decision priorities: which outcome wins when simplicity, speed, control, extensibility, cost, or accuracy conflict.
  • Constraints: externally imposed boundaries, their owners, and the distinction between hard requirements and preferences.
  • Open decisions: what remains unresolved, who can resolve it, and which work depends on it.

Discovery questions. Who has this problem, and what can they not accomplish today? What observable change would make the project worthwhile? What must it never become? Which attractive feature should be rejected? What commitments already constrain the answer? Who can change the goal?

Inference boundary. The skill can extract candidate goals and contradictions from supplied conversations and existing records. It can summarize an explicitly approved decision. It should not silently infer market demand, promised deadlines, numerical targets, stakeholder agreement, or which value wins a trade-off from code alone. Unconfirmed interpretations remain proposals, with their source and uncertainty.

Minimal outline. Purpose → People and problem → Desired outcome → Scope and exclusions → Priorities and constraints → Unresolved decisions → Authoritative links. Optional metadata identifies owner and status. Illustrative content: “Help volunteer coordinators fill uncovered shifts; payroll and staff performance scoring are outside scope.” This is an example, not an assumed requirement.

Validation and upkeep. Ask the owner to test the draft against one desirable and one deliberately rejected feature. Revisit intent when the audience, mission, or material constraint changes. Keep detailed feature acceptance in specs, implementation rationale in ADRs, and contributor procedures in their own guide. A README can summarize the purpose and link to intent; it should not maintain a second set of exclusions.

Proposed generator instruction

Draft purpose from the brief. Ask for decisions that materially change scope or priorities. Preserve uncertainty. Do not turn an incidental implementation limitation into permanent product policy.

Baseline responsibilityGLOSSARY.md / domain CONTEXT.mdCanonical terms, distinctions, relationships, and context-specific meanings.

Purpose and creation trigger. Proposed design: create a glossary when an overloaded word, relationship, lifecycle, or invariant can change behavior. Resolve the first meaningful ambiguity before accumulating a long dictionary. Reuse GLOSSARY.md, CONTEXT.md, or an existing domain guide. In this repository's domain-modeling convention, CONTEXT.md means a glossary; its name must not become permission to add arbitrary project notes.

Shared vocabulary supports communication between developers and domain experts; where meanings differ legitimately, scope the definitions rather than forcing one global interpretation. Ubiquitous Language, Bounded Context.

Proposed content domains:

  • Actors and roles: who does what, and distinctions such as person, organization, member, administrator, and service account.
  • Business objects: identity, ownership, meaningful relationships, and what makes two instances distinct.
  • Lifecycle vocabulary: states, transitions, events, and the difference between an action and its completed result.
  • Rules expressed as definitions: invariants and distinctions needed to understand a concept.
  • Boundaries and translations: context-specific meanings, synonyms, deprecated terms, external-system mappings, units, and time conventions.
  • Examples and counterexamples: one instance that belongs and a similar one that does not.

arc42 includes technical terminology too. Proposed adaptation: include only project-specific technical meanings that readers can realistically confuse; do not reproduce a programming dictionary. arc42 glossary.

Discovery questions. Does “account” mean a login, customer, or billing relationship? Can one person hold several memberships? Is cancellation reversible? Does “published” mean visible, approved, or delivered? Does a word mean something different in another subsystem? Which terms do domain experts actually use?

Inference boundary. Names and schemas reveal candidate vocabulary and implemented relationships. They do not establish that the business meaning is correct. The skill should surface disagreement between code and owner descriptions, not automatically choose the code. Owners resolve business semantics; observed code can be marked as current implementation.

Minimal outline. Scope → Terms → Relationships → Context differences → Unresolved vocabulary. A useful entry is Term | Meaning | Scope | Example or distinction. Example: “Reservation: a temporary claim on capacity; expires unless confirmed. Booking: a confirmed allocation.” For a simple project, prose definitions alone suffice.

Validation and upkeep. Walk through counterexamples, plural ownership, duplicates, missing states, and boundary transitions. Search documentation and code for conflicting names. Update the canonical entry when meaning changes; record significant migration rationale elsewhere. Keep API field shapes in contracts, database storage in schemas, future requirements in specs, and decision history in ADRs. Introduce a context map only when multiple models actually need explanation.

Proposed generator instruction

Reuse the existing glossary. Define meaningful project concepts. Test ambiguity with examples and counterexamples. Keep implementation decisions, task status, and operating policy elsewhere.

Baseline responsibilityREADME.mdThe human entry point and a runnable first success.

Purpose and creation trigger. This is the visitor's entry point and the usual minimal documentation for a newly shareable repository. It answers whether the project is relevant, what exists now, and how to reach a useful first result. GitHub's guidance directly supports this role. About READMEs.

Proposed content domains: identity and purpose; current maturity and limitations; intended users; a concrete usage example; prerequisites and installation; first successful execution; expected output; documentation navigation; support and maintainers; contribution and license links. Separate using a released tool from developing its source when those paths differ. Avoid presenting planned capabilities as available.

Discovery questions. Who arrives here first: end users, contributors, operators, or evaluators? What should they accomplish in five minutes? Is installation from a release, package manager, or checkout? Which environments are supported? Where should a person report a problem? Is the project experimental or production-supported?

Inference boundary. The skill can inspect package metadata, existing license text, runnable commands, and examples. It can report checks it actually performed. It cannot infer a support commitment, compatibility guarantee, license choice, maturity label, or contact owner's consent merely from the repository's existence.

Minimal outline. What this does → Status and audience → Quick start → Example and expected result → Documentation → Help and contributing → License. Purpose and status deserve deliberate attention because the empirical README study found these were often missing. Prana et al..

Validation and upkeep. Try the quick start in an appropriate clean environment or clearly state which steps remain unverified. Check links and referenced files, commands, prerequisites, and output. Update it when installation, user-visible behavior, or support routes change. Summarize architecture rather than copying its full document; link contribution rules and detailed references. For an empty new repository, describe the planned state explicitly and avoid fictional executable examples.

Proposed generator instruction

Write the shortest path from an unfamiliar reader to a useful result. Link authoritative design and workflow documents. Report planned or unverified capabilities honestly.

Baseline responsibilityAGENTS.md and scoped instructionsA concise operating guide and routing map for compatible agents.

Evidence. The AGENTS.md convention is plain Markdown with no required schema. Its examples cover overview, setup, tests, style, and security. It supports nested instructions for subprojects. Actual loading and precedence should still be checked against the selected agent tools rather than assumed universally. AGENTS.md.

Creation trigger: baseline for repositories intended to be maintained by agents. Generate only repository-specific guidance that is already known or deliberately chosen.

Content domains and subdomains: orientation (purpose in one paragraph; document map); execution (working directory, setup and focused/full checks); modification constraints (generated files, public interfaces, compatibility expectations); local conventions that tooling cannot communicate; change workflow (canonical issue/spec, evidence required at completion); and links to authoritative policy. Add nested files when a package really has different commands or constraints, not mechanically in every folder.

Discovery questions: Which agents will work here? Which tasks and commands are routine? Which paths are generated? Which mistakes would a competent new contributor otherwise make? What actions has the owner actually authorized?

Facts versus decisions: inspect manifests, scripts and generator headers for facts. Obtain workflow expectations from the owner or existing approved guidance. Do not convert a template's sample permission into authority to commit, push, publish, create pull requests, deploy or change repository settings. A repository file cannot override higher-priority user or platform instructions.

Minimal outline: Purpose; Read next; Commands; Change constraints; Completion evidence. Prefer links over duplicated architecture, domain definitions and product requirements.

Validation/upkeep: check links and referenced paths; execute safe documented commands; compare command descriptions with actual behavior. Revisit when scripts, package boundaries, generation processes or owner policy change. Record unavailable checks honestly.

Proposed generator instruction

Document specific constraints and real commands. Link deeper material with a reading trigger. Avoid duplicating lint configuration or loading every document for every task. Verify behavior in the chosen agent.

Create when neededARCHITECTURE.mdModules, responsibilities, dependency direction, and important constraints.

Purpose and creation trigger. Explain the system's important parts, relationships, and boundaries. Create a compact map once there is an agreed initial design or meaningful code; a tiny repository can keep this in its README. Matklad recommends a short document focused on stable structure, coarse modules, architectural invariants, and crosscutting concerns. His original recommendation targets roughly 10k–200k-line open-source projects, so applying the filename to every newborn repository is an extrapolation. ARCHITECTURE.md

Domains and subdomains to consider. Use these as prompts, not mandatory empty headings:

  • System boundary: actors, external services, inputs/outputs, and responsibilities outside this repository.
  • Structural map: major packages or modules, their responsibilities, entry points, data ownership, and public interfaces.
  • Dependency rules: allowed directions, prohibited imports, isolation boundaries, and important absences.
  • Runtime behavior: one or two representative request, job, or event flows; state transitions; concurrency and failure boundaries when relevant.
  • Deployment shape: executable units, persistent stores, external infrastructure, and environment differences that affect design.
  • Crosscutting concerns: authentication, authorization, configuration, errors, observability, serialization, caching, and migrations, selecting only consequential topics.
  • Quality constraints: measurable architectural requirements and known risks, linked to their canonical requirement or decision records.

arc42 supplies a broader menu covering context, building blocks, runtime, deployment, quality, risks, and crosscutting concerns. It explicitly allows tailoring; its twelve sections need not become twelve files. arc42 overview

Questions the setup skill should ask. What will run independently? Where is state owned? Which integrations or trust boundaries are already committed? What interactions must remain impossible? Which quality goals actually influence design? Which parts are deliberately undecided?

Infer versus decide. Read package manifests, entry points, imports, deployment configuration, and existing contracts to describe observable structure. In a new repository, label an unimplemented design as proposed. Never infer an accepted business boundary, service split, performance target, or permission policy merely from common templates. A directory called services does not establish a microservices architecture.

Minimal outline. Status and scope → System context → Module/responsibility table → Allowed dependency directions and invariants → Representative flow → Crosscutting concerns → Risks and linked decisions.

Validation and upkeep. Check named paths and interfaces exist, diagrams agree with the map, and dependency rules have executable checks where feasible. Review after changing a boundary, public interface, deployment unit, or state owner. Stable explanatory prose needs semantic review; generated inventories need regeneration. Do not require rewriting the map for every internal function change.

Keep elsewhere. Product purpose belongs in INTENT.md; term definitions in GLOSSARY.md; command recipes in development docs; detailed rationale in ADRs; task status in issues/plans. Link those sources.

Diagrams. C4 distinguishes context, container, component, and code views and says most teams need only context and container views. The skill should add only diagrams that resolve a real question, with labeled relationships and a plain-text explanation. For a library, a public API/module map may be more useful than a deployment diagram. C4 diagrams

Create when neededdocs/decisions/ — ADRsOne consequential choice, its rationale, status, and consequences.

Purpose and creation trigger. Preserve why a consequential choice was made. Nygard's ADR pattern uses one small record per significant decision, with context, decision, status, and consequences. Keep superseded records and point to their replacements. A setup skill can initialize a template and index, but should write an accepted ADR only for a real choice the owner has made. Documenting Architecture Decisions

Domains and subdomains. Candidate decisions include component boundaries, data ownership, storage, protocols, dependencies, deployment, compatibility, consequential workflow constraints, and crosscutting security or reliability approaches. Within each record capture the specific problem; relevant constraints and priorities; actual considered options; chosen option; reasons; benefits; costs; consequences; affected contracts; and any revisit trigger. Describe rejected options honestly. Do not invent an evaluation process after the fact.

Questions. What decision is being made now? What alternatives were genuinely considered? Which requirement favored the winner? What cost are we accepting? Who can accept the choice? What evidence or changed condition would justify revisiting it?

Infer versus decide. An installed database proves a dependency exists; it does not prove why it was selected. If rationale is unavailable, record the observed state and the missing rationale explicitly. Ask for consequential preferences; identify drafts as proposed. Avoid a fictional first ADR declaring every generated convention accepted.

Minimal outline. Identifier/title → Status/date → Context and drivers → Considered options → Decision and rationale → Consequences → Links/revisit conditions.

Validation and upkeep. Check unique identifiers, nonempty project-specific rationale, explicit status, and reciprocal supersession links. An accepted decision must match actual owner authorization. When a choice changes, write the replacement record and preserve the former context. Correct factual errors without rewriting history to imply the replacement was always intended. An index lists current and superseded decisions; it does not duplicate their arguments.

Separation. Architecture describes the current structure. An ADR explains a particular choice. Intent establishes the project-level priority; the ADR records how that priority influenced one decision. A transient debugging guess usually belongs in an issue, not an ADR.

Baseline responsibilitySpecifications and acceptance criteriaObservable behavior for the first useful outcome and subsequent changes.

Purpose and creation trigger. Proposed design: create a spec for an agreed change when behavior, edge cases, interfaces, or measurable quality need coordination. A small fix can use acceptance criteria in its existing issue; do not create a second spec solely to satisfy a filename checklist. Reuse an established Spec Kit, OpenSpec, issue, or requirements workflow.

Proposed content domains: actors and prioritized journeys; inputs and outputs; authorization and ownership; identity and lifecycle; success, empty, loading, and failure states; integration failures; concurrency and retry behavior; externally relevant compatibility; measurable quality constraints; exclusions, assumptions, and open questions. Apply only relevant domains and explain deliberate omissions. This coverage adapts Spec Kit's clarification categories; its proposed interviews prioritize questions whose answers materially alter implementation or validation. Clarification workflow.

Discovery questions. What exact behavior would make the owner accept this change? Which negative case must fail? Who can perform each action? What happens on a duplicate request or unavailable dependency? What existing consumer must remain compatible? Which quality targets are commitments, and how will they be measured?

Inference boundary. Existing tests and APIs provide evidence of current behavior and candidate regression constraints. They do not authorize a new product policy. The skill can propose examples, identify missing cases, and derive checks from explicit requirements; owners decide changed behavior, risk tolerance, retention, authorization rules, priorities, and numerical service targets.

Minimal outline. Change and source intent → User scenarios → Requirements → Acceptance examples → Edge cases → Quality constraints → Assumptions and unresolved decisions → Validation evidence. Spec Kit's template uses identified requirements and measurable outcomes; adopting its complete directory layout is optional. Spec template.

Illustrative criterion: “Given a full shift, when another volunteer requests it, then the request is rejected with a capacity explanation and no reservation is created.” State the result visible to an actor or external system. Plain Markdown criteria are valid documentation; Gherkin becomes an executable test only with its implementation and runner. Gherkin reference.

Validation and upkeep. Require each accepted requirement to have a checkable outcome, and distinguish a proposed check from executed evidence. Exercise a normal, denied, boundary, and recovery case where applicable. Trace implementation and tests back to requirements; revise the spec when intent changes, preserving the decision record. Keep work sequencing in plans/tasks, reusable definitions in the glossary, and enduring architectural decisions in ADRs. A spec describes the contract; a green test run is evidence about that contract, not automatic proof that every requirement was covered.

Proposed generator instruction

Make done observable. Derive scenarios from stated needs, include meaningful failures, and identify unknowns. Keep sequencing in plans and implementation rationale in decision records.

Baseline responsibilitySetup and command entry pointsReproducible install, start, check, and regeneration paths.

Evidence. For npm projects, npm ci requires a lockfile, rejects a mismatch with the manifest, and does not update either file. This is a concrete example of a frozen installation mechanism, not a reason to select npm for every project. npm ci.

Creation trigger: baseline once the repository has an executable or generated deliverable. A pure prose repository may only need its preview and document checks.

Artifact family: package/build manifest, appropriate lockfile, runtime declaration, setup/check scripts, .env.example when environment variables exist, and a concise setup guide. A dev container or compose file is conditional on real environment complexity.

Domains: prerequisites (supported OS/runtime/tools); dependencies (installation and update mechanisms); configuration (variable names, required/optional status, safe examples); local services (startup, seed data, shutdown); commands (dev, build, focused checks, full checks); outputs (generated paths); and repeatability (deterministic inputs, ports, isolated state).

Discovery questions: What deliverable must run? On which systems? Which external services are required? Can a useful local mode run without production credentials? Which steps alter data or access paid services?

Facts versus decisions: inspect the selected stack; label chosen runtime targets and new scripts as proposals until implemented. Secret values are never scaffold content. Portability and supported-version promises need owner intent.

Minimal outline: Requirements; Install; Configure; Run; Check; Troubleshooting. Each command needs its working directory and expected observable result. The command manifest is canonical; prose explains purpose and prerequisites.

Validation/upkeep: perform a clean setup where practical, then start and exercise the smallest useful feature. Confirm a repeated setup does not duplicate or destroy user data. Distinguish “script exists,” “executed successfully,” and “verified on all supported platforms.” Update together with dependencies and environment changes.

Proposed generator instruction

Implement commands before documenting them as available. Run a clean setup and the smallest useful check. Introduce containers or task runners only when they solve a real need.

Starter outline or example

Create when neededInterfaces, contracts, and dependency mapsPrecise agreements between independently changing parts.

Purpose and creation trigger. Give independently changing parts an explicit agreement. A new repository needs enough structure to keep responsibilities clear; it does not automatically need a CONTRACTS.md, schema directory, and graph generator. Add stronger machinery when there are independently consumed APIs, multiple packages, external data formats, or important layering constraints.

arc42's building-block guidance offers a useful per-module baseline: responsibility, interface, location, relevant quality characteristics, and risks. It recommends selectively expanding surprising, risky, or complex blocks. This supports describing a module as a useful boundary instead of duplicating all implementation details. arc42 building-block view

Domains and subdomains. Our proposed contract checklist covers:

  • Ownership: responsibility, state owned, callers, dependencies, and public entry points.
  • Shape: input/output types, required fields, identifiers, units, nullability, validation, and version semantics.
  • Behavior: side effects, invariants, error categories, partial failure, ordering, idempotency, retries, and cancellation where applicable.
  • Change: compatibility promises, deprecation, migration responsibilities, examples, and executable contract checks.
  • Dependency map: nodes, relationship kinds and direction, source evidence, generated versus reviewed content, and exclusions with reasons.

Questions. Who consumes this boundary? What compatibility do we promise? What must callers never access directly? Can a call be repeated safely? Who owns data migrations? Which relationships can be extracted mechanically, and which are semantic?

Infer versus decide. Extract imports, exports, signatures, schema fields, and declared dependencies. Confirm intended public stability and behavior separately. Import absence does not prove a deliberate prohibition. An auto-generated graph describes detected relationships; it cannot certify that those relationships are good architecture.

Minimal outline. A module table plus native interface declarations usually suffices: Module → Responsibility → Public interface → Owned state → Dependencies → Invariants → Verification. Put HTTP details in an OpenAPI document when applicable: operations, request/response schemas, parameters, errors, and security descriptions. OpenAPI is specifically a human- and machine-readable description for HTTP APIs, not a universal module-contract format. OpenAPI specification

Validation and upkeep. Type-check interfaces; validate schemas and examples; exercise important boundary behavior; compare consumer expectations with providers; flag unintended breaking changes. For JavaScript/TypeScript, dependency-cruiser is a concrete example of a tool that extracts dependencies, checks configured rules, and generates diagrams. Its existence shows these checks are implementable; selection still depends on the stack. dependency-cruiser

Separation. Keep machine-readable declarations canonical. Architecture summarizes boundaries and links to contracts. Avoid a second manually maintained field catalog in Markdown. Generated graph checks and semantic relationship review are different responsibilities.

Proposed generator instruction

Keep native contracts authoritative. Generate representations where practical. Distinguish detected dependencies from reviewed semantic relationships and intended architecture.

JSON Schema provides a vocabulary for documenting and validating JSON shapes; specifying types and constraints is meaningful, whereas an empty schema constrains nothing. GitHub Actions, JSON Schema.

Creation trigger: a minimal verification path belongs in the baseline. Add schema contracts for actual structured boundaries and architecture checks for explicit architectural rules. Add remote CI when the hosting and execution policy are known.

Domains: behavior (critical use cases, failures, edge cases); boundaries (API, file, configuration and data contracts); invariants (permitted dependency directions, generation consistency); quality (formatting, lint, type checks); execution (fixtures, isolation, external-service requirements); and results (exit status, useful diagnostics, reproducible failing inputs). Discovery questions: What outcome must never regress? What would count as evidence that the initial feature works? Which input boundaries can reject invalid data? What checks are cheap enough for every edit? Which require credentials, significant time or money?

Facts versus decisions: framework configuration and existing checks are facts. Risk tolerance, coverage goals, required checks and supported environments are design decisions. Avoid arbitrary coverage percentages and nominal tests that only confirm a scaffold exists.

Minimal outline for an optional TESTING.md: Check commands; What each establishes; Fixtures; Local/CI differences; Known gaps. Start with a representative behavior test and a useful aggregate check, not an empty directory for every test category.

Prove a useful behavior works and a meaningful invalid case fails for the right reason. Distinguish package-format validation from behavioral evaluation. Record what actually ran.

Evidence. Anthropic's harness uses an initializer, a feature list and progress records so subsequent sessions can recover state and verify incremental work. Evidence. OpenTelemetry identifies traces, metrics and logs as different signals about system behavior. These categories help organize diagnostics; adopting its entire toolchain is not required for a small repository. OpenTelemetry signals.

Creation trigger: every executable needs understandable failures; a service, recurring job or operational procedure may justify docs/runbooks/. A library may only need error conventions and a reproducer recipe.

Domains: symptoms; scope/environment; health checks; relevant logs and correlation identifiers; metrics and expected bounds; reproductions; likely causes and discriminating checks; mitigations; rollback/recovery; post-action verification; and escalation contacts. 05 / Proposed skill workflow

Discover → resolve → generate → verify

This is a proposed algorithm for a future repo-creation skill.

  1. Inspect the starting state. Determine whether the repo is empty, a template, or existing work. Read applicable instructions and inspect files, manifests, docs, tests, CI, and environment. Preserve existing work.
  2. Build an evidence ledger. Separate supplied intent, verified facts, explicit decisions, proposals, and unknowns. Keep the source of each consequential claim. An empty repo naturally has more proposals than verified implementation.
  3. Select a profile and canonical homes. Assign each responsibility to an existing file, a new file, an accessible external record, or a reasoned omission.
  4. Resolve high-impact unknowns. Ask an adaptive interview: purpose/users/outcomes, scope/non-goals, ambiguous terms, platform/environment, public interfaces, important quality constraints, and actual authorization/review/release policy. Skip answered questions. Present a recommended default when useful.
  5. Draft meaning before mechanics. Establish intent and agreed language; specify one first useful outcome; propose the minimum architecture and interfaces needed to support it. Label unimplemented or unaccepted material.
  6. Implement runnable entry points. Add stack-appropriate commands and useful checks within the authorized scope. Then document them. Do not advertise tools or tests that do not exist.
  7. Write navigation and agent instructions. Produce README and concise AGENTS.md after canonical content exists. Add task-based reading triggers; verify any client-specific compatibility files.
  8. Check consistency and usefulness. Run checks, compare terms and claims, find duplicated policy, and exercise representative tasks. Fix mechanical problems before asking the owner to resolve purpose or policy.
  9. Present a concrete setup report. List created/reused/omitted files, decisions, open questions, checks and outcomes, and unverified limitations. Preserve action-specific authorization for commits, pushes, PRs, releases, and external configuration.

Sample intake

  • Who is the primary user, and what first outcome makes this repo useful?
  • Which adjacent problems are explicitly outside scope?
  • Which two or three terms could an unfamiliar agent misunderstand?
  • Which environment, integrations, or compatibility promises are fixed?
  • What result would prove the initial implementation works?
  • Which owner policies already govern external actions and delivery?

Inspect first and ask only unanswered questions whose answers matter. A general-purpose questionnaire should not force a library author to define incident staffing or a content repo to choose a database.

Output states

Ready: required decisions are resolved, populated artifacts reflect evidence, and applicable checks pass.

Draft with explicit unknowns: useful work exists, but a consequential decision, dependency, or check is unresolved. Name its consequence and the smallest next step.

No change needed: existing artifacts already meet the relevant responsibilities. Report that finding and narrowly justified gaps.

A second run should reconcile changes, preserve accepted content, and avoid duplicate files or falsely refreshed review dates.

06 / Verification

A reviewable acceptance contract

Check Passing evidence Failure to catch
Purpose fidelity Intent traces to the brief or explicit decisions Invented audience, business goal, or compliance obligation
Vocabulary Terms agree; context differences are explicit “Release” changes meaning between intent and workflow
Navigation Targets exist; important sources are discoverable A glossary exists but the agent never learns to consult it
Runnable setup Setup and smallest check run, or limits are reported README names a nonexistent command
Meaningful verification A valid case passes and a relevant invalid case fails correctly A check always succeeds or only mirrors implementation
Architecture fidelity Observed/proposed structure are distinct; important rules have checks A diagram claims a dependency prohibition without evidence
Authority Policies and actions reflect actual authorization A generated file grants itself publication permission
Minimality Every artifact answers a distinct useful question Empty ADRs, speculative layers, padding, duplicate policies
Repeatability Rerun preserves accepted content and makes evidence-backed updates Duplicate glossaries or needless whole-file rewrites

Evaluate the eventual skill on diverse fixtures

Try an empty repo with a vague brief; an existing repo with a canonical glossary; a one-file CLI; a monorepo with scoped vocabulary; a repo with contradictory commands; and a skills package with format checks but no behavior evaluation.

Judge resulting files and environment outcomes, not just an agent's claim of compliance. Anthropic's eval guidance distinguishes task, trial, grader, transcript, and final outcome.

Proposed measures: unsupported claims, broken links, command success, conflicting duplicate sources, preservation of existing work, unresolved consequential choices, and human review effort. These are design criteria for this skill, not published universal thresholds.
