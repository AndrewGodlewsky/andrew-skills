Skill loading · prompt assembly · context economics

What actually enters
the context window?

A technical account of discovery, invocation and resource loading—and what those mechanisms mean for keeping GT skills small without making their architecture vague.

Research delegated to a subagent; repository evidence and synthesis reviewed by the main agent. Primary focus: Copilot CLI and VS Code. Other harness behavior is identified separately.

01 / Executive model

A skill is stored as files.
A harness decides what the model sees.

There is no universal operation that puts an entire skill directory into a model. The client discovers files, interprets supported fields, builds a request, and exposes some content immediately while leaving other content available through tools. Reading a file on the host and sending that file to the model are different events. This is the most useful distinction for your architecture decision.

Before invocation

A discoverable description may already cost context

The common design advertises a skill's name and description, sometimes its path, without its full instructions. Catalog eligibility, placement and filtering are harness choices. A manual-only skill's treatment must be checked for the actual client, not inferred from its presence in a menu. [1]

At invocation

The selected instructions become model input

A dedicated skill tool, explicit command expansion, or ordinary file read can supply the instructions. Some routes retain YAML; others strip it. A body-only explanation is not a universal byte-level guarantee. [1]

Direct answer to your concern: extra Markdown headings are ordinary text once their file is loaded. They can organize behavior, but they do not create new loading stages. Extra frontmatter can affect parsing or client behavior. Extra files usually require a later read to contribute their contents, but their filenames or paths can still be advertised. These are three different architectural changes, with different consequences.

What is already clear for GT: keep task-essential instructions short and self-contained; keep evidence written only for reviewers outside the runtime instructions. What still needs your decision: the exact required header fields and extension policy. This report does not treat that proposal as approved.

02 / A precise vocabulary

Separate storage, parsing, disclosure and execution

BoundaryWhat happensWhat it does not establish
1. Filesystem / packageThe skill folder contains instructions, metadata and optional resources. A client can enumerate or cache these bytes locally.That those bytes were tokenized into any model request.
2. Harness stateThe parser produces an internal record: identity, description, location and supported control fields. The UI and tool layer can use it.That every parsed key is shown to the model or that unknown keys have meaning.
3. Model requestThe assembled messages, tool definitions, attached text and other inputs are submitted for an inference step.That all earlier local reads are present, or that the UI transcript reveals the full request.
4. Runtime effectsThe harness executes approved tool calls, supplies results, and continues the conversation.That merely loading a skill grants new permissions, executes its scripts or guarantees the model follows it.

This is an analytical model, not a claim about one fixed serialization format. It explains why an inventory command can list a skill whose body has never entered the conversation, and why a file can be fully parsed on the host while only its description is disclosed.

Do not collapse four meanings of “loaded”

Installed means files exist in a usable location. Discovered means the harness found a candidate. Advertised means the current model request can identify it. Activated means its instructions were supplied through the selected route. A fifth question—whether those instructions remain in the current request after context management—cannot be answered just by saying the skill was activated earlier.

Two different activation paths

MODEL-SELECTED
request with skill advertisements
  → model chooses a skill / file-read tool
  → harness resolves and returns or injects instructions
  → next inference step can use those instructions

USER-SELECTED
explicit command or attachment
  → harness may resolve instructions before inference
  → first request for that turn may already contain the skill

Neither path implies that every resource in the folder was read.

A command string that merely appears in ordinary prompt text is not proof that the client intercepted it. That matters in automated tests: the repository's old noninteractive probe forced a skill-tool call through a deterministic responder; it did not test an interactive slash-command picker. [7]

Where can skill text appear in a request?

Potential routes include tool-result content, an attached context block, or an expanded user message. A catalog may sit in prompt text or a tool description. These alternatives are relevant because logging one channel is not enough to reconstruct the full model input. The integration guide explicitly permits multiple integration patterns; it is guidance for implementers, not evidence that Copilot uses every pattern. [1]

What the pinned VS Code source actually does

Source inspection Revision 981b8c60abe325ad32cdebfddbf1d34ace34bd72, inspected September 16, 2026. This is a code snapshot, not verification of your installed client.

  1. Discovery: the plugin parser reads the local document and extracts name, description and invocation flags. Reading the file here does not mean its body enters a model request.
  2. Automatic catalog: the index builder filters manual-only skills. Eligible entries carry name, description and file path. With the skill tool enabled, it caps full entries at 15,000 characters, then permits up to 5,000 characters of remaining names. These are source-path character limits, not token budgets or CLI constants; later request assembly can impose other limits.
  3. Inline skill tool: the tool's loader uses the full document, including YAML, plus its base directory. Its related-file helper lists at most 50 paths with a recursion-depth limit of five; it does not insert those files' contents.
  4. Another rendering route: the prompt attachment renderer computes a body offset to remove frontmatter. We did not trace every slash-command route into it. This establishes route dependence, not a universal rule for explicit invocation.

The detailed evidence memo records additional paths, conditions and unresolved questions. No repetition guard was found inside the inspected skill-tool invoke method; that does not establish whether higher layers deduplicate it.

What this report deliberately does not generalize

Claude Code, Codex, Copilot CLI and VS Code can share a skill format while using different catalogs, wrappers and context-management behavior. “It works this way in a skills-compatible client” is not sufficient evidence for a GT guarantee. This report's proposed GT authoring practices aim to remain useful across those differences, rather than relying on an undocumented prompt position.

05 / Your architecture question

“Add a category” can mean four different changes

ChangeContext implicationBehavior / compatibility implication
A heading in the bodyIts text is part of the loaded instructions. It does not provide independent lazy loading.Useful organization for the model; does not automatically become an enforced schema or workflow state.
A new YAML keyMay remain host metadata or also appear in activated text, depending on the route.May be recognized, ignored or rejected by different parsers. Parsing success does not prove functional support.
A separate bundled referenceThe filename/path may be advertised; the content enters a request when read or attached.The skill must give a usable reason/path to read it. Critical always-needed constraints should not depend on a merely optional read.
A repository-only review recordIt is outside the normal skill package and need not be a routine skill dependency.Good for author/reviewer evidence, but unavailable to an isolated exported skill unless separately supplied. Not a secrecy boundary.

Control fields versus descriptive fields

Some recognized frontmatter controls a harness decision. Other text explains purpose to the model. A custom field is not automatically in either group. If GT adds category: writing, first identify its consumer: is it for a repository index, validation, a user-facing catalog, or runtime behavior? Without a consumer it is maintenance data, not a new capability.

A scalar can pass this repository's current parser and still be meaningless to the client. Conversely, a field allowed by a wider format can fail the local parser: its current implementation expects simple single-line values and does not implement arbitrary nested YAML structures. For example, the standard's metadata mapping is not automatically supported by our validator. [2] [9]

A header is not a permissions sandbox

The CLI documents allowed-tools in terms of automatic allowance, which makes it more than prerequisite documentation. [4] GT should not add such a field simply to say “this skill needs Git.” A runtime prerequisite, eligibility to select a skill, and authorization to perform a tool action are distinct decisions. The accepted export prerequisite does not authorize installations, publishing or changes to security controls.

Does a Markdown section affect model behavior even if no code interprets it?

Yes, as ordinary language. A heading can help the model distinguish “Inputs” from “Expected result,” and an example can strongly steer the output pattern. That is a semantic effect, not parser enforcement. A section named “Required” does not prove the model complied, and a section named “Optional” does not prevent its tokens from entering context when the whole body is loaded. This is why structural consistency and behavioral evaluation should be designed separately.

06 / Second-order context costs

A file can be available without its contents being present

Think of a resource link as an address and an instruction to fetch, not as textual inclusion. A model that sees references/format.md knows where to obtain information; it does not necessarily know the file's content. A harness can list filenames without reading them into the request, and it can read a file locally without including its entire contents in the returned tool result.

Reference read

Body: “For the CSV mode, read
references/csv-rules.md.”

CSV requested → file-read call
             → returned rules enter context
Other mode  → no reason to fetch the file

Design illustration. The instruction encourages conditional access; it does not impose a hard client access restriction.

Script execution

Execute scripts/check.mjs
  → OS/runtime reads script bytes
  → process emits stdout/stderr
  → tool returns selected output

Separate read of check.mjs
  → source text enters model input

Conceptual distinction. Actual tool wrappers can add summaries, truncation or other context.

Executing a helper and reading its source are not the same cost. A helper may process a large dataset and emit one useful result, or it may emit thousands of irrelevant lines. Moving work into a script therefore does not guarantee smaller context: the output contract is as important as the source-file size. Similarly, logging an entire configuration, error object or report can bring information back into context that never appeared in the skill body.

For historical GT copies, every execution dependency still needs to travel with the exported folder or be an explicitly supported external prerequisite. Moving necessary runtime instructions into a repository-only test record would make an apparently lean skill incomplete. Moving reviewer rationale there does not have that problem. This is a consequence of the accepted export contract, not an additional loader feature.

07 / Context accounting

Optimize what crosses the request boundary

The most useful budget is a decomposition, not a single “tokens per skill” number:

Current input ≈ other conversation/context
+ skill advertisements included now
+ activated skill content retained now
+ resource contents and tool results retained now
+ wrappers, filenames, paths and tool schemas

This is an accounting model, not a documented Copilot billing formula. Content may be filtered, deduplicated, summarized or truncated. Provider tokenization and request layout also matter. A count of source-file bytes is not a request token count.

What the model teaches us

  • Long descriptions can impose a repeated discovery cost across many eligible skills, even when only one is used.
  • A lean body reduces selected-skill input, but a routinely loaded giant reference can erase that saving.
  • Offloading optional detail helps when it is genuinely optional. “Read all references before starting” makes the split mostly organizational.
  • Review evidence outside routine execution avoids requiring every skill invocation to repeat a development review.
  • Helper output can dominate everything else; design concise results and useful error reports.

These are deductions from the accounting model, not measured savings for this repository. There is no recommended numerical limit hidden in the sliders.

08 / Across turns

“Loaded once” does not mean “free forever”

After activation, skill-related text can affect later turns if it remains in the request history or retained context. The fact that a client avoids another disk read does not establish that the text is absent from the next inference input. Conversely, the fact that an earlier UI transcript contains the text does not establish that the client still sends it verbatim.

MechanismSeparate question to ask
Filesystem / parser cacheDoes the client reread changed SKILL.md bytes? This concerns freshness and I/O, not automatically inference cost.
Prompt cachingDoes the provider reuse computation for a matching input prefix? That is not proof of unlimited context capacity or a permanent loaded skill.
History trimming / compactionWhich instructions, summaries or skill identifiers survive? Can the client re-read the source when needed?
Subagent / forked contextWhich input goes to the child, which result returns to the parent, and what inherited context or repeated work adds cost?
Session restart / resumeIs the skill resolved afresh, replayed from history or reconstructed? Installed version alone cannot answer this.

These are verification questions, not assertions of a particular Copilot retention algorithm. VS Code documents an experimental forked-context option, but it is not a portable GT assumption or a promise of a clean context. [3] This research does not recommend adopting it just to reduce the size of a simple skill.

Implication for the versioning plan: an on-disk update and the instructions driving an existing conversation can diverge. The agreed status report should continue to describe installed files, not claim to identify the skill text currently influencing a chat.

10 / Recommendation for this project

Standardize the contract.
Keep the executable guidance compact.

Design recommendation The research supports the direction you preferred, with one correction: do not assume the header is invisible after activation. Treat every word in SKILL.md as potentially model-visible on a full-file route.

A practical litmus test for every sentence

Ask: does the executing agent need this to select, perform or correctly limit the task? If yes, put it in the appropriate runtime surface. If it exists to explain why the maintainer approved the design, how the contribution was tested, or which issue discussed it, it normally belongs in review evidence. Some examples genuinely improve execution; those can remain with the skill. This is an authoring judgment, not a rule to remove all examples.

Mechanical validation can establish that required files exist, field types are valid and resource links resolve. It cannot prove that instructions are sufficient, minimal or followed. A short focused skill plus a meaningful external test case is often more auditable than a long template with many empty or generic sections. This is our design inference, not an additional client requirement.

11 / What remains unknown

Separate design confidence from runtime proof

The open questions are concrete enough to test later, without adding a testing requirement to your review now:

  1. Pre-invocation disclosure: compare model-visible advertisements for all supported combinations of invocation flags, including plugin and personal sources.
  2. Serialization: place distinct harmless markers in name, description, body, a custom field, a reference and a release sidecar; observe where each appears in messages and tool schemas.
  3. Loading versus read: distinguish a listed resource path from its contents and a script's source from its output.
  4. Repeated invocation and updates: change a disposable fixture between turns and observe cached versus fresh content; do not infer it from the installed version.
  5. Retention: repeat around actual context compaction/resume in a disposable environment and document what can be observed.
  6. Client parity: compare exact CLI/VS Code versions and invocation routes; use supported diagnostic hooks without collecting unrelated prompts or credentials.

This is a proposed measurement plan, not a claim that every client exposes an adequate diagnostic interface. If visibility is insufficient, the result remains unknown. No bypass of authentication, trust or security controls is implied.
