Agent handoff · Architecture & implementation

Ship custom agents inside your existing Copilot plugin.

Add Markdown agent definitions alongside the plugin’s skills. Keep the existing plugin identity and marketplace entry so users receive both through the same installation.

Prepared October 13, 2026 · Reference project: AndrewGodlewsky/andrew-skills, plugin gt · Self-contained HTML; no external assets or scripts

1. Intent and scope

The owner wants to author Markdown files that become selectable custom Copilot agents and distribute them through an existing plugin marketplace project. The agreed design keeps those agents inside the existing plugin alongside its skills. A new marketplace listing or separate agent plugin is unnecessary for this goal.

MarketplaceThe catalog where users find the existing plugin.
Existing pluginThe package users install and update.
Skills + custom agentsComponents delivered inside that package.

A custom agent provides a reusable role, instructions, and tool configuration in a .agent.md file. VS Code supports selecting these agents for a conversation. Custom agent documentation.

The filename distinction is settled. This request concerns custom agent definitions such as reviewer.agent.md. It does not ask to create or modify the repository instruction file AGENTS.md.

The owner has not chosen actual agent roles, names, tools, or workflows yet. “Reviewer” and “planner” below are original examples for implementation discussion, not approved product requirements. This handoff itself does not install agents, change a plugin, or authorize publication.

2. Folder structure

GT currently declares the Agent Plugins 1.0 schema. For that format, the documented Copilot agent location is com.github.copilot/agents/ relative to the plugin root. VS Code and Copilot CLI document this layout. VS Code layout · CLI layout.

Proposed GT layout. The agents folder and example files are additions, not existing implemented agents.

andrew-skills/                         ← repository / marketplace root
├── .claude-plugin/
│   └── marketplace.json               ← existing catalog entry for gt
└── plugins/
    └── gt/                            ← plugin root
        ├── plugin.json                ← existing plugin identity
        ├── skills/
        │   ├── grill-me/
        │   │   ├── SKILL.md
        │   │   └── release.yaml       ← GT convention
        │   └── ...
        └── com.github.copilot/
            └── agents/
                ├── reviewer.agent.md  ← example addition
                └── planner.agent.md   ← example addition

In another project, substitute the plugin directory selected by that project’s marketplace entry. A plugin rooted directly at the repository root would use com.github.copilot/agents/reviewer.agent.md there. The plugins/gt/ prefix is GT’s repository organization, not a universal Copilot requirement.

Keep one existing marketplace entry for the selected plugin. The namespace folder has no separate plugin manifest or installation identity. Other existing plugins in the receiving marketplace remain independent and unchanged.

3. Detect the receiving project’s format first

Read the selected plugin’s manifest before copying the GT path. The current creation guide distinguishes schema-based Agent Plugins packages from legacy Copilot packages. Legacy packages retain their own component locations. GitHub’s plugin creation guide.

What you findImplementation route
Root plugin.json declares https://agent-plugins.org/schemas/1.0.0/plugin.schema.jsonUse com.github.copilot/agents/*.agent.md beneath that plugin root.
Legacy Copilot manifest without that schemaUse its configured agent directory, or the documented agents/ default. Preserve the format unless migration is separately requested.
Claude-format package, a different schema version, or multiple candidate manifestsResolve the active format against the intended client’s current documentation. Record the chosen root and discovery path before editing.

For Agent Plugins 1.0, a top-level "agents" path field is not part of the portable manifest; Copilot components use the namespace directory. A default-location agent addition does not need an invented manifest extension. The portable component types are skills and MCP servers; custom agents remain client-specific. Manifest rules.

Implementation recommendation: retain the target project’s format, marketplace identity, unrelated manifest fields, and release conventions. Avoid expanding a small agent addition into a plugin migration.

Agent A: review text supplied in chat

New file: plugins/team-tools/com.github.copilot/agents/proposal-reviewer.agent.md

---
name: proposal-reviewer
description: Review a supplied proposal for missing decisions and unclear requirements.
tools: []
user-invocable: true
disable-model-invocation: true
---

Review the proposal supplied in the conversation against the user's stated goal.
If the proposal or goal is missing, ask for the missing input.

Identify up to five issues that would materially affect implementation.
For each issue, explain the consequence and recommend a concrete revision.
Distinguish missing evidence from a demonstrated problem.

Return findings in chat. If there are no material issues, say so and identify
any assumptions that still need verification. Do not claim to inspect files,
run checks, or change the project; this agent has no tools.

This is a small discovery test: it can perform its stated job using only conversation content. GitHub documents tools: [] as disabling tools; omitting tools instead defaults to all available tools. description is required by GitHub’s agent configuration reference. Agent configuration.

Agent B: inspect a repository and propose a plan

New file: plugins/team-tools/com.github.copilot/agents/repository-planner.agent.md

---
name: repository-planner
description: Inspect relevant project files and propose a bounded implementation plan.
tools: [read, search]
user-invocable: true
disable-model-invocation: true
---

Use the user's requested outcome to identify the smallest relevant area of the
project. Read applicable repository guidance and inspect the existing behavior.
If the outcome is unclear, ask a focused question before settling the plan.

Return:
1. The intended behavior and supporting file references.
2. The proposed changes, grouped by purpose.
3. Checks that would demonstrate the requested behavior.
4. Open decisions and any evidence you could not obtain.

Keep this task to inspection and planning. Do not edit files or claim that
proposed checks have passed. If reading or searching is unavailable, explain
the limitation and request the relevant material.

The read and search aliases appear in GitHub’s configuration reference. Check the actual tool resolution in each supported client. That reference also documents the two invocation flags; these examples choose manual selection. Unknown tools can be ignored, so successful file parsing is insufficient evidence of usable capabilities. Tool configuration.

VS Code offers additional features such as model selection, handoffs, and subagent configuration. Those can be added when a role needs them; they introduce additional behavior to validate. These starter definitions deliberately leave the model unspecified and do not orchestrate other agents. VS Code agent options.

Authoring recommendation: choose tools from the agent’s job, write a concrete output contract, and test a missing-input case. Keep runtime instructions inside the distributed package. If an agent depends on a skill, specify when and how it should use that skill and test the dependency in the client; co-location alone is not a workflow.

5. Implementation sequence for the receiving agent

  1. Establish the target. Read repository instructions, inspect the working tree, and identify the existing marketplace entry, plugin root, format, and intended Copilot clients. Completion: record those facts with paths and client versions.
  2. Define the first agent. Use the owner’s supplied role and behavior. Where those are absent, propose one minimal role and clearly label it as a proposal. Completion: name, inputs, output, tools, invocation choice, and failure behavior are explicit.
  3. Add the definition. Create a single .agent.md file in the format-appropriate directory. Preserve existing skills and other plugin contents. Completion: the new agent is within the selected plugin’s package boundary.
  4. Review distribution and checks. Inspect packaging filters, export steps, validation, version-change detection, and tests. Completion: agent files are included in the shipped package and meaningful validation covers their format. Existing skill checks remain intact.
  5. Update relevant documentation. Explain the agent’s role, how to find it, its requirements, and its limits. Apply the project’s release rules to the bundle. Completion: documentation describes the actual implementation and distinguishes observed support from planned support.
  6. Verify the experience. Run repository checks and client tests from the next section. Completion: report exact checks, versions, observed results, and remaining gaps.
  7. Prepare the owner’s review. Provide the changed files and a concise result. Keep commits, pushes, PR creation, publishing, and merges within the target repository’s authorization rules. Completion: the owner can assess both behavior and remaining release work.

For validators, prefer a small extension to existing checks: require a meaningful description and nonempty body, validate YAML types, detect duplicate identities, and reject an agent misplaced outside the selected package. Check the current supported frontmatter rather than applying a skill-only allowlist to agent files. Add tests only where they verify these actual constraints or release behavior.

7. Troubleshooting decision guide

These are suggested diagnostic branches, not claims about a particular failure.

Observed symptomNext inspection
Plugin appears; agent does notCompare the loaded manifest format with the agent directory. Confirm suffix, YAML, manual visibility flag, packaged file presence, and current client support.
Old agent behavior after editingCompare loaded package bytes with the source. Refresh the managed test copy and use a fresh session.
Two similar agent entriesInspect workspace, personal, and plugin definitions; establish source identity before removing anything.
Agent appears but cannot inspect codeCheck resolved tools and the active harness. Compare the tool list with current client documentation.
Repository validation passes, client discovery failsCheck whether validation actually parses agent definitions or only inspects existing skills/manifests.
Published installation misses the new filesInspect marketplace source/ref, release version, package include/exclude rules, and installed revision.
Instructions assume an unavailable skillMake the dependency explicit, validate discovery/invocation, and supply a clear missing-dependency response.

8. GT-specific context to carry forward

The following facts were read from the reference checkout on October 13, 2026. They explain the origin of this design; they are not requirements for an unrelated repository.

  • plugins/gt/plugin.json declares Agent Plugins 1.0, plugin name gt, and version 0.1.23.
  • .claude-plugin/marketplace.json names marketplace andrew-skills and contains a single gt entry pointing to ./plugins/gt, with matching version.
  • scripts/validate.mjs enforces that single-plugin arrangement, validates manifest fields, and passes discovered skills through skill validation. The inspected validation function has no dedicated custom-agent parser.
  • scripts/release-snapshots.mjs reads the plugins/gt tree. A future implementation should still verify agent-only release detection and validation end to end.
  • CONTRIBUTING.md is the current authoring/release guide. GT uses per-skill release.yaml metadata and one plugin patch increment per bundle change. It does not establish a per-agent metadata format; do not invent one merely by copying skill packaging.
  • The root AGENTS.md requires maintainer review of GT Help when skills or marketplace guidance change, and dependency-map maintenance for applicable skill/shared-source changes. Apply those procedures when implementing affected changes in GT.

GT Help was inspected for this handoff. Its published guidance remains unchanged because this document proposes future custom-agent support and does not add an agent or change the shipped catalog. A real GT implementation should update affected Help guidance in the same change.

The request fulfilled here is a transferable HTML handoff. It makes no claim that GT already ships the example agents. GitHub issue authority granted for the GT repository does not transfer to another project, nor does it authorize Git publication.

9. Brief to give the receiving agent

Task: add custom Markdown agents to our existing Copilot plugin

Use this handoff as implementation context. Identify our existing marketplace entry and plugin root, read our repository instructions, and determine the active plugin format. Keep the agents inside the selected plugin alongside its skills.

For an Agent Plugins 1.0 package, use com.github.copilot/agents/*.agent.md relative to the plugin root. For another supported format, use its documented agent location. Preserve the current plugin identity and other marketplace entries.

Implement the agent roles supplied with this request. If roles have not been supplied, propose a minimal first agent and resolve the missing behavioral requirements before treating example roles as final. Include meaningful descriptions, explicit tool choices, instructions, expected output, and missing-input handling.

Review packaging, validation, release handling, and user documentation for the addition. Test discovery and behavior in each Copilot client we intend to support, plus an existing skill. Report unavailable client tests honestly.

Return changed paths, the final folder structure, each agent’s purpose, checks and observed results, remaining limitations, and publication steps still awaiting the owner’s authorization. Use our project’s authorization rules for commits, pushes, PRs, merges, and releases.

Definition of done

  • The correct existing plugin contains the agent definitions.
  • The marketplace still exposes the intended existing plugin identity.
  • The shipped package includes agents and preserves existing skills.
  • Agent purpose, tools, visibility, inputs, and outputs are documented.
  • Validation covers the new file type and relevant release changes.
  • Claimed clients pass discovery and representative behavior tests, or the result is explicitly marked partial with outstanding tests.
  • The final handoff distinguishes implemented work, verified behavior, and pending publication.
