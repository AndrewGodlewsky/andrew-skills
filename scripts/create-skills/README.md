# Creator tools

Maintained local modules for `skills/create-skills`. Build with
`node scripts/build-create-skills.mjs`; `--check` verifies generated bytes and
the canonical authoring-rule excerpt without writing. Repository-only tooling
changes do not require edits to unrelated distributed skills.

The package exposes `check <directory>`, `prepare`, `next` and `install` through
its bundled run.mjs. The latter three accept a bounded JSON object on stdin;
stdout is one JSON result. These tools never authenticate or contact GitHub.
The creator must actually invoke the enabled model-invocable create-issue skill
for each returned submission/reconciliation request. This is an instruction-level
dependency boundary; the local planner cannot prove model selection occurred.

| Boundary | Responsibility |
| --- | --- |
| skill-package-validation.mjs | Extracted pure GT header/release/link rules, shared by repository validation. |
| package.mjs | Bounded regular-file snapshot, source identity, standalone diagnostic report. No draft execution. |
| submission.mjs | Canonical text/file serialization and stateless next-operation calculation from actual evidence. |
| install.mjs | Explicitly approved, ordinary-name, create-only copy to the active user's home. |
| run.mjs | Command/input validation and bounded JSON I/O. |

Input/status contracts are documented in the bundled conditional references.
Issue checks are advisory: a complete specification remains submittable when
package construction or checking fails. Installation requires a stable input
identity and structurally usable package; adoption retains repository release
validation. Neither copying nor a structural pass proves client invocation.

Filesystem checks reject observed symlinks/junctions, hard-linked source files,
case-colliding names, unsupported entries, traversal and excessive size/count.
Files are read through checked handles with bounded allocation. Destination
files use exclusive creation and SKILL.md is staged then published last with an
atomic no-replace hard link. Unsupported publication is reported without a
rename/overwrite fallback. Failures retain a
reported partial destination; there is no recursive cleanup or automatic retry.
These portable Node operations do not provide a transactional filesystem or an
OS-enforced sandbox against a hostile process concurrently replacing ancestors.
Use a user-controlled draft and destination, not a shared adversarial directory.

Submission evidence lives in the calling workflow. The planner does not write a
transport ledger, resume cache or hidden idempotency marker. A candidate found
after a lost response must pass the dependency's read-only known-ID/content check;
no replay follows from an empty list or an uncertain response. `present` means
expected content exists, not proof that this attempt created it. Cross-call
pacing remains the caller's responsibility (at least one second between writes).

The tests include real submission-service logic behind simulated GitHub responses,
copied-package CLI runs, a temporary isolated personal home and injected local
write failures. These are offline tests, not a Copilot conversation or a live
GitHub submission. Windows/Linux Node 22/24 jobs are configured in CI; report the
actual executed matrix separately.
